# 06 · 编译器与图优化

> **本模块回答**：上面这些需求，怎么自动翻译成高效代码？

前五个模块里的优化，大多是"人工发现一个模式，然后写一个系统"。编译器要做的是**把这种发现过程自动化**。
本模块的收益是长期的：它训练你看待"一个模型 = 一堆算子 + 一堆数据依赖"的眼光。

## 本模块的核心思想：计算与调度分离

同一个计算（例如矩阵乘），可以用完全不同的执行方式实现（分块大小、循环顺序、是否向量化、如何分配 shared memory）。
**"算什么"和"怎么算"是两件事**——把二者解耦，就能把"怎么算"交给搜索与自动调优。这是整个机器学习编译器领域的基石。

## 论文清单

### 1. TVM（本模块的地基）

- [ ] **P0** ⭐ · [TVM: An Automated End-to-End Optimizing Compiler for Deep Learning](https://arxiv.org/abs/1802.04799) · OSDI 2018
  - **主旨**：提出 **计算与调度分离**：用 `compute` 描述"算什么"，用 `schedule` 描述"怎么算"（tile、reorder、vectorize、unroll、bind）。再配合基于机器学习的自动调优（autotuning）为每个算子搜出最优 schedule，并能针对不同硬件后端生成代码。
  - **为什么读 / 读到什么程度**：**精读前 4 节 + 看懂一张 schedule 变换图**。这是理解 Ansor、TensorRT、TorchInductor 乃至所有"算子优化"工作的前提。你要能看懂下面这段直觉：
    ```python
    # compute：算什么
    C = te.compute((M, N), lambda i, j: te.sum(A[i, k] * B[k, j], axis=k))
    # schedule：怎么算（这里只是示意）
    s = te.create_schedule(C.op)
    xo, xi = s[C].split(C.op.axis[0], factor=64)   # 分块
    s[C].bind(xo, te.thread_axis("blockIdx.x"))    # 映射到 GPU block
    ```
  - **前置知识**：03 模块的 tiling 概念。
  - **建议用时**：4 小时。
  - **读完要能回答**：为什么"手工为每种硬件写算子库"不可持续？（硬件碎片化 + 模型结构变化快 + 组合爆炸。）

### 2. MLIR

- [ ] **P0** · [MLIR: A Compiler Infrastructure for the End of Moore's Law](https://arxiv.org/abs/2002.11054) · 2020
  - **主旨**：传统编译器只有单一层次的 IR，而 AI 编译需要从"高层框架图"一路降到"硬件指令"，跨越多个抽象层级。MLIR 提出**可扩展的多层方言（dialect）+ 渐进式 lowering**，每层只做该层擅长的优化。
  - **为什么读 / 读到什么程度**：**泛读**。重点理解 dialect / operation / pass 的概念，以及"为什么需要多个 IR 层级"。
  - **前置知识**：第 1 篇。
  - **建议用时**：2 小时。
  - **为什么它重要**：今天几乎所有 AI 编译基础设施（包括 TorchInductor、Triton、各家芯片公司的编译器栈）都建在 MLIR 上。它是一个"学会了就一直有用"的知识点。

### 3. Ansor

- [ ] **P0** · [Ansor: Generating High-Performance Tensor Programs for Deep Learning](https://arxiv.org/abs/2006.06762) · OSDI 2020
  - **主旨**：TVM 的 schedule 需要人手工指定模板（template），泛化性差。Ansor 自动**构造搜索空间**：先生成大量候选的"计算图 sketch"（高层结构），再用演化搜索 + 学到的代价模型挑出好的，最后做精细调优。不需要任何手写模板。
  - **为什么读 / 读到什么程度**：**泛读**。读第 3 节（搜索空间的构造）与第 4 节（代价模型）。理解"搜索空间的设计比搜索算法本身更重要"。
  - **前置知识**：第 1 篇。
  - **建议用时**：2.5 小时。

### 阶段 B：图级优化 —— "改写计算图本身"

#### 4. TASO

- [ ] **P1** · [TASO: Optimizing Deep Learning Computation with Automatic Generation of Graph Substitutions](https://cs.stanford.edu/~zhihao/papers/sosp19.pdf) · SOSP 2019
  - **主旨**：图级优化长期依赖人工写规则（如"conv+relu 可以融合"）。TASO 自动**生成并验证**图重写规则：先用算子规范自动生成候选替换，再用形式化方法验证等价性，最后搜索最优图。
  - **为什么读 / 读到什么程度**：**泛读**。读第 3、4 节。重点理解"等价性是自动化图优化的前提"。
  - **前置知识**：第 1 篇。
  - **建议用时**：2 小时。

#### 5. Equality Saturation for Tensor Graph Superoptimization

- [ ] **P1** · [Equality Saturation for Tensor Graph Superoptimization](https://arxiv.org/abs/2101.01332) · MLSys 2021
  - **主旨**：TASO 的搜索是逐条规则贪心的，容易陷入局部最优。这篇用 **e-graph（等价类图）** 同时表示所有等价的图形态，在等价闭包上做饱和式探索，再抽取最优表达。这是编译器领域"等价饱和"技术首次成功应用于张量图。
  - **为什么读 / 读到什么程度**：**泛读**。理解 e-graph 的核心直觉：**位置无关地表示所有可能的写法**。
  - **前置知识**：第 4 篇。
  - **建议用时**：2 小时。

#### 6. Rammer

- [ ] **P1** · [Rammer: Enabling Holistic Deep Learning Compiler Optimizations with rTasks](https://www.usenix.org/conference/osdi20/presentation/ma) · OSDI 2020
  - **主旨**：TVM/Ansor 在算子内部优化，但算子之间的并行与数据依赖没人管。Rammer 用 rTask 抽象把"算子内"和"算子间"的优化统一起来，让硬件能被真正打满。
  - **为什么读 / 读到什么程度**：**泛读**。重点理解"跨算子的并行度不足"这个问题。
  - **前置知识**：第 1、3 篇。
  - **建议用时**：1.5 小时。

#### 7. Welder

- [ ] **P1** · [Welder: Scheduling Deep Learning Memory Access via Tile-graph](https://www.usenix.org/conference/osdi23/presentation/shi) · **OSDI 2023**
  - **主旨**：把优化目标直接对准"内存访问"而非"指令数"：用 tile-graph 显式建模数据在 DRAM/L2/shared memory 之间的流动，在多个算子之间做全局的访存调度。
  - **为什么读 / 读到什么程度**：**泛读**。它把 01 模块的"带宽才是瓶颈"贯彻到了编译器层面，是两模块的连接点。
  - **前置知识**：第 1、3 篇；01 模块。
  - **建议用时**：1.5 小时。
  - **注意**：这篇常被误标成 NSDI；**正确出处是 OSDI 2023**。

### 阶段 C：工业实践

#### 8. TorchInductor

- [ ] **P1** · [TorchInductor: a PyTorch-native Compiler with Define-by-Run IR and Symbolic Shapes](https://dev-discuss.pytorch.org/t/torchinductor-a-pytorch-native-compiler-with-define-by-run-ir-and-symbolic-shapes/747) · 2023（官方技术说明）
  - **主旨**：PyTorch 官方编译后端的设计说明：用 Python 实现 IR、支持动态形状、把算子融合后生成 Triton kernel。它是 02 模块那个历史遗留问题（"动态图如何拿回静态图的优化能力"）的当代答案。
  - **为什么读 / 读到什么程度**：**泛读**。读设计动机与 IR 部分即可。
  - **前置知识**：02 模块第 2、4 篇；本模块第 1、2 篇；03 模块第 3 篇（Triton）。
  - **建议用时**：1.5 小时。
  - **为什么放在最后**：读完它，你能把 02 → 03 → 06 三个模块串成一条完整的线：**动态图 → 图捕获 → 图级优化 → 算子生成（Triton）**。

## 动手验证（这一周必做）

1. **（必做）跑通 TVM 或 Ansor 的自动调优**：用 TVM 为一个矩阵乘指定几组不同的 schedule（不同 tile 大小），实测性能差异；再用 Ansor 的自动搜索跑同一个矩阵乘，对比"人找的"和"机器找的"。
2. **写一个 schedule**：用 TVM 的 te/schedule 为一个 `conv + relu` 写 schedule，手动做算子融合，理解融合为什么能省访存。
3. **（可选）看一次 TorchInductor 的产物**：用 `TORCH_COMPILE_DEBUG=1` 或设置 `torch._inductor.config.debug`，把 `torch.compile` 生成的 Triton kernel 打印出来看，确认你读的论文和眼前的代码是一回事。

## 演进链（谁替代了谁）

```
手写算子库（cuDNN 等）—— 不可持续：硬件多、模型变、组合爆炸
    ↓
TVM（2018）：计算与调度分离 + 自动调优 —— 地基
    ↓
  ├─ 调度问题：Ansor（2020）自动构造搜索空间，不再需要手写模板
  ├─ 图级问题：TASO（2019）自动生成重写规则 → Equality Saturation（2021）e-graph 全局搜索
  ├─ 跨算子问题：Rammer（2020）rTask 统一算子内外 → Welder（2023）以访存为目标的全局调度
  └─ 基础设施：MLIR（2020）多层方言 + 渐进 lowering，成为业界标准底座
    ↓
工业界收敛：TorchInductor + Triton（2023）—— 动态图直接编译到高效 kernel
```
