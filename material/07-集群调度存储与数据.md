# 07 · 集群调度、存储与数据

> **本模块回答**：多个任务、上千张卡，怎么调度、怎么不丢进度？

前六个模块都在优化"一个任务内部的效率"。真实的生产系统面对的是完全不同的问题：**任务会失败、卡会坏、资源是共享的、别人也在抢**。
本模块把视角从"单任务性能"拉到"集群级 goodput"，这也是 AI Infra 岗位与纯算法岗最明显的区别。

## 论文清单

### 1. 分布式执行底座

- [ ] **P0** ⭐ · [Ray: A Distributed Framework for Emerging AI Applications](https://arxiv.org/abs/1712.05889) · OSDI 2018
  - **主旨**：AI 应用同时需要"无状态任务并行"（如超参搜索）和"有状态计算"（如参数服务器）。Ray 用统一的抽象（task / actor + 分布式对象存储 + 动态任务图）把两者装进同一个系统，并靠 GCS（全局控制存储）做低延迟的调度与容错。
  - **为什么读 / 读到什么程度**：**精读架构、泛读实现**。重点理解：(1) 为什么不能用 MPI/Spark 的模型套 AI 负载；(2) 分布式引用计数与对象存储是怎么让数据在节点间高效共享的。
  - **前置知识**：上面的分布式基础。
  - **建议用时**：3.5 小时。
  - **为什么它排第 1**：今天的分布式训练框架、RLHF 框架（如 verl）、超参搜索、推理编排，大量建在 Ray 之上。它是集群侧的通用底座。

### 2. 通信架构之争

- [ ] **P0** · [A Unified Architecture for Accelerating Distributed DNN Training in Heterogeneous GPU/CPU Clusters (BytePS)](https://www.usenix.org/conference/osdi20/presentation/jiang) · OSDI 2020
  - **主旨**：AllReduce（如 NCCL/Ring）在**同构**集群里很高效，但在"少量 GPU + 大量 CPU"的异构场景下带宽利用极差。BytePS 用参数服务器架构 + 分级通信 + 流水线，把 CPU 机器的带宽也用起来。
  - **为什么读 / 读到什么程度**：**泛读**。重点理解 AllReduce 的适用前提，以及"通信拓扑要匹配集群形态"这个结论。
  - **前置知识**：04 模块的集合通信。
  - **建议用时**：2 小时。
  - **读完要能回答**：什么情况下你会选参数服务器而不是 AllReduce？

### 3. 调度：从"利用率"到"有效吞吐"

- [ ] **P1** · [Pollux: Co-adaptive Cluster Scheduling for Goodput-Optimized Deep Learning](https://arxiv.org/abs/2104.08803) · OSDI 2021
  - **主旨**：GPU 利用率高 ≠ 训练有效。Pollux 让调度器与训练任务**互相适配**：调度器动态调整给每个任务的资源量，任务同时动态调整 batch size 与学习率。共同优化 goodput（有效吞吐）而不是利用率。
  - **为什么读 / 读到什么程度**：**泛读**。重点理解 goodput 的定义以及"资源变化时训练超参必须跟着变"这一关键洞察。
  - **前置知识**：01 模块（知道为什么调度器需要理解性能模型）。
  - **建议用时**：2 小时。

- [ ] **P1** · [Sia: Heterogeneity-aware, Goodput-optimized ML-cluster Scheduling](https://arxiv.org/abs/2306.14086) · SOSP 2023
  - **主旨**：真实集群是异构的（不同代际 GPU），Pollux 的假设不再成立。Sia 通过轻量的 profiling 在异构资源上做细粒度调度，把作业分配到"最合适的那一类卡"上，并支持抢占与抢占后的快速恢复。
  - **为什么读 / 读到什么程度**：**泛读**。与 Pollux 对照读，理解"假设变了，调度器要怎么变"。
  - **前置知识**：Pollux。
  - **建议用时**：1.5 小时。

### 4. 容错与 checkpoint

- [ ] **P1** · [Gemini: Fast Failure Recovery in Distributed Training with In-Memory Checkpoints](https://dl.acm.org/doi/10.1145/3600006.3613166) · SOSP 2023
  - **主旨**：模型越大，写一次 checkpoint 到磁盘的代价越高（GB 级 → TB 级），故障恢复时间成为集群利用率的主要杀手。Gemini 把 checkpoint 放在**主机内存**里，配合分块、异步与层级式写入，大幅缩短恢复时间。
  - **为什么读 / 读到什么程度**：**泛读**。重点理解"恢复时间如何直接影响集群成本"，这是很多人想不到的 Infra 问题。
  - **前置知识**：04 模块（知道模型状态有多大）。
  - **建议用时**：2 小时。
  - **注意（重要）**：**这是本清单唯一需要机构访问的论文**——只有 ACM 出版页链接（`10.1145/3600006.3613166`），浏览器在校园网/机构代理下可访问。若访问受限，可先跳过，或在 Google Scholar 搜索论文名找作者提供的副本。

- [ ] **P2** · [Bamboo: Making Preemptible Instances Resilient for Affordable Training of Large DNNs](https://www.usenix.org/conference/nsdi23/presentation/thorpe) · NSDI 2023 —— 用便宜的可抢占实例训大模型，靠冗余计算和流水线重排来对抗频繁中断。
- [ ] **P2** · [Singularity: Planet-Scale, Preemptible and Elastic Scheduling of AI Workloads](https://arxiv.org/abs/2202.07848) · 2022 —— 微软的生产级弹性调度系统报告，能看到真实集群的调度约束。
- [ ] **P2** · [AntMan: Dynamic Scaling on GPU Clusters for Deep Learning](https://www.usenix.org/conference/osdi20/presentation/xiao) · OSDI 2020 —— 在 Kubernetes 之上动态共享 GPU 显存与算力，是多租户集群的基础能力。

## 动手验证（这一周必做）

1. **（必做）用 Ray 起一个最小分布式任务**：写一个 Ray task 做并行计算，再用一个 Ray actor 保存状态。体会"无状态并行 + 有状态计算"两种抽象的区别——这正是第 1 篇论文的出发点。
2. **算一次 checkpoint 成本**：假设一个 70B 模型、每张卡 200 GB/s 的写入带宽，算出写一次 FP16 checkpoint 需要多久、占训练时间的比例。你会立刻理解 Gemini 要解决的问题有多重要。
3. **（可选）观察一次 AllReduce**：用 `torch.distributed` 起 2–4 个进程，跑一次 all-reduce，改变消息大小并记录耗时，观察小消息时"延迟主导"、大消息时"带宽主导"的分界点。

## 演进链（谁替代了谁）

```
MPI / Spark 时代的通用分布式框架 —— 不匹配 AI 负载的形态
    ↓
Ray（2018）：task + actor + 分布式对象存储，成为 AI 集群通用底座
    ↓
通信：AllReduce（同构）↔ 参数服务器（异构，BytePS 2020）
    ↓
调度：利用率优先 → goodput 优先（Pollux 2021）→ 异构感知（Sia 2023）
    ↓
容错：磁盘 checkpoint（慢）→ 内存 checkpoint（Gemini 2023）→ 免 checkpoint 恢复（前沿方向）
    ↓
今天：Kubernetes + Ray + 专用调度器（各云厂商自研）构成的生产栈
```
