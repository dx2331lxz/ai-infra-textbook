# 02 · 框架与自动微分

> **本模块回答**：你天天在用的 PyTorch，背后到底做了什么？

这一模块看起来"离 Infra 很远"，实际上它是你和硬件之间的那一层抽象。
读懂它，你才会明白后面所有系统论文在对抗什么：**动态图的灵活性，是用执行效率换来的**；**显存不够，是因为 autodiff 把中间结果全留着了**。

## 论文清单

### 1. Automatic Differentiation in Machine Learning: a Survey

- [ ] **P0** ⭐ · [Automatic Differentiation in Machine Learning: a Survey](https://arxiv.org/abs/1502.05767) · JMLR 2018
  - **主旨**：把 autodiff 的三种模式（前向模式、反向模式、以及基于 tape / 伴随法的实现）讲清楚，并区分 autodiff、符号微分、数值微分。
  - **为什么读 / 读到什么程度**：**精读概念**，不追求读完 40 多页。重点是：为什么反向模式的代价与"输出维度"成正比，而不是与参数量成正比——这正是神经网络训练可行的数学原因。
  - **前置知识**：链式法则。
  - **建议用时**：4 小时（读第 1–5 节为主）。
  - **为什么它排第 1**：**显存是 AI Infra 的头号约束**，而显存的主要占用者（激活值）就是 autodiff 的副产品。理解 forward 时保留了哪些张量，你才能理解第 04 模块里 ZeRO 和重计算（recomputation）在优化什么。

### 2. PyTorch: An Imperative Style, High-Performance Deep Learning Library

- [ ] **P0** · [PyTorch: An Imperative Style, High-Performance Deep Learning Library](https://arxiv.org/abs/1912.01703) · NeurIPS 2019
  - **主旨**：PyTorch 的设计论文。核心是 define-by-run：计算图在执行时才被构建出来，带来调试便利，也带来"无法提前做全局优化"的代价。
  - **为什么读 / 读到什么程度**：**泛读**。读第 2 节（设计原则）和第 3 节（实现：dispatcher、算子注册、异步执行）。你要理解的是"Python 每行都在发算子，调度开销不可忽略"这一点。
  - **前置知识**：第 1 篇。
  - **建议用时**：2 小时。
  - **读完要能回答**：为什么 PyTorch 需要 `torch.compile` 和 TorchInductor？（这个问题会在第 06 模块得到完整答案。）

### 3. TensorFlow: A System for Large-Scale Machine Learning

- [ ] **P1** · [TensorFlow: A System for Large-Scale Machine Learning](https://www.usenix.org/system/files/conference/osdi16/osdi16-abadi.pdf) · OSDI 2016
  - **主旨**：define-and-run 的数据流图范式：先建图、全局优化、再执行。与 PyTorch 形成对照面。
  - **为什么读 / 读到什么程度**：**泛读**。读第 2 节（数据流模型）和第 3 节。重点理解"图先建好，编译器才有全局视野"——这是第 06 模块编译器优化的前提。
  - **前置知识**：第 2 篇。
  - **建议用时**：1.5 小时。
  - **为什么这个对照重要**：整部 AI Infra 史有一条主线就是"如何在保持动态图易用性的同时拿回静态图的优化能力"，一直延续到今天的 TorchInductor 和 Triton。

### 4. JANUS: Fast and Flexible Deep Learning via Symbolic Graph Execution of Imperative Programs

- [ ] **P1** · [JANUS: Fast and Flexible Deep Learning via Symbolic Graph Execution of Imperative Programs](https://www.usenix.org/conference/nsdi19/presentation/jeong) · NSDI 2019
  - **主旨**：第一次系统化尝试"写的是动态图代码，执行时自动追踪成静态图再优化"。
  - **为什么读 / 读到什么程度**：**泛读**。读摘要 + 第 3 节机制。它是 `torch.jit` / `torch.compile` 的思想祖先。
  - **前置知识**：第 2、3 篇。
  - **建议用时**：1 小时。

### 5. Dynamic Tensor Rematerialization

- [ ] **P1** · [Dynamic Tensor Rematerialization](https://arxiv.org/abs/2006.09616) · ICLR 2021
  - **主旨**：把"显存溢出时该怎么办"形式化为一个**缓存置换/调度问题**：显存不够时丢掉中间张量，需要时重算；核心是给出一个代价模型来决定丢谁。
  - **为什么读 / 读到什么程度**：**泛读**。读摘要 + 系统设计 + 与"静态重算"的对比实验。
  - **前置知识**：第 1 篇（知道哪些张量是 autodiff 留下的）。
  - **建议用时**：1.5 小时。
  - **为什么重要**：这是"用计算换显存"这一大类技术的理论化表述。第 04 模块的 activation recomputation / sequence parallelism 都是它的工程化版本。

### 6. 补充选读（P2）

- [ ] **P2** · [micrograd 源码](https://github.com/karpathy/micrograd) · 100 行左右的 autodiff 实现 —— **强烈建议真的读一遍**，不到 1 小时。
- [ ] **P2** · [tinygrad 源码](https://github.com/tinygrad/tinygrad) · 一个"极简但完整"的深度学习框架，包含 kernel 生成。适合在读完第 03、06 模块后回来看。
- [ ] **P2** · 任意一篇重计算/显存优化方向的论文（搜 "activation checkpointing survey"）。

## 动手验证（这两周必做）

1. **手写 autodiff**：跟着 [micrograd](https://github.com/karpathy/micrograd) 自己实现一个 `Value` 类，支持 `+ - * /`、`relu` 和 `backward()`。用两层 MLP 训练一个 XOR 验证正确。这一步做完，你就永久掌握了反向传播的机制，而不只是会调用它。
2. **观察显存**：用 PyTorch 训一个很小的模型，在 forward 和 backward 处打印 `torch.cuda.memory_allocated()`。观察 backward 结束后**激活值才被释放**。这就是 ZeRO 和重计算要解决的问题来源。
3. **数一下调度开销**：用 `torch.profiler` 抓一个小模型的一条训练 step，看看 GPU kernel 之间有多少空隙、CPU launch 了多少个 kernel。你会亲眼看到"框架层的开销是真实存在的"。

## 演进链（谁替代了谁）

```
符号式（TF 1.x, 建图后执行）
    ↕  PyTorch 用动态图胜出（易调试，但丢失全局优化）
JANUS（动态图 → 追踪成静态图）
    ↓
TorchScript / torch.compile / TorchInductor（第 06 模块）
    ↓
Triton 让"图优化后的算子"能高效落地（第 03 模块）

autodiff 留下的激活值 → 显存墙
    ↓
动态重算（本篇）→ 静态重算 + 序列并行（第 04 模块）→ ZeRO / FSDP（第 04 模块）
```
