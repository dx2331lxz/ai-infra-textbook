# 04 · 训练系统与并行策略

> **本模块回答**：一个几百 GB 甚至上 TB 的模型，怎么放到几千张卡上训出来？

**这是全清单的重心，也是 AI Infra 面试与科研最密集的区域**，建议投入 3 周而不是 2 周。
整个模块其实只在解决两个约束的对抗：**显存不够** 和 **通信太慢**。每一篇论文都是在二者之间找一个更好的平衡点。

## 一张贯穿全模块的账（先记住，再读论文）

一个 $P$ 参数、用 Adam 训练的模型，FP16 混合精度下每张卡要放：

| 项目 | 字节数（相对参数量） | 说明 |
| --- | --- | --- |
| 参数（FP16） | 2P | |
| 梯度（FP16） | 2P | |
| 优化器状态（FP32 参数副本 + 动量 + 方差） | 12P | **最大的一块** |
| **合计** | **16P** | 不含激活值 |

所以一个 7B 模型仅"模型状态"就要 **112 GB**，一张 80GB 的卡都放不下——这就是 ZeRO 存在的理由。
再叠加激活值，才是真正引发所有并行策略的原因。

## 论文清单

### 阶段 A：流水线并行 —— "把模型按层切开"

#### 1. GPipe

- [ ] **P0** ⭐ · [GPipe: Efficient Training of Giant Neural Networks using Pipeline Parallelism](https://arxiv.org/abs/1811.06965) · NeurIPS 2019
  - **主旨**：把模型按层切到多卡，一个 batch 切成多个 micro-batch 灌进流水线，让各段并行起来。代价是流水线"气泡"（bubble）：空闲等待时间。
  - **为什么读 / 读到什么程度**：**精读**。必须自己算一次：$p$ 段流水线、$m$ 个 micro-batch 时，气泡占比是多少？（$O(p/m)$。）这个公式后面会被反复引用。
  - **前置知识**：上面的 16P 账。
  - **建议用时**：3 小时。
  - **读完要能回答**：为什么 micro-batch 数越多，气泡越小，但显存占用越大？

#### 2. PipeDream

- [ ] **P0** ⭐ · [PipeDream: Generalized Pipeline Parallelism for DNN Training](https://arxiv.org/abs/1806.03377) · SOSP 2019
  - **主旨**：针对 GPipe 的问题（一个 step 内 forward/backward 交替导致显存峰值高、吞吐低），PipeDream 提出 1F1B（one forward one backward）调度，让各段在稳态下交替执行，显存占用大幅下降。代价是权重陈旧（stale weights）——它用异步梯度换取效率。
  - **为什么读 / 读到什么程度**：**精读**。重点读 1F1B 调度图和第 4 节的显存分析。**这张调度图（GPipe vs 1F1B vs 交错式）是 AI Infra 最高频的面试题之一**，务必能手画。
  - **前置知识**：第 1 篇。
  - **建议用时**：3.5 小时。
  - **优势与代价**：优势是显存与吞吐；代价是引入权重陈旧性，可能影响收敛。

### 阶段 B：张量并行 —— "把单个算子切开"

#### 3. Megatron-LM

- [ ] **P0** ⭐ · [Megatron-LM: Training Multi-Billion Parameter Language Models Using Model Parallelism](https://arxiv.org/abs/1909.08053) · 2019
  - **主旨**：流水线并行解决不了"单层太大"的问题。张量并行把**单个矩阵乘**按列/行切开：MLP 用 Column Parallel + Row Parallel 配对，让一次 all-reduce 就能补回完整结果；attention head 天然可切。
  - **为什么读 / 读到什么程度**：**精读**。必须自己推一遍：为什么 `Y = GeLU(X·A)` 用列切分后不需要立即通信，而 `Z = Y·B` 用行切分后才需要一次 all-reduce？为什么是**每两层一次通信**而不是每层两次？
  - **前置知识**：第 1、2 篇；矩阵乘的分块。
  - **建议用时**：4 小时。
  - **读完要能回答**：张量并行和流水线并行的通信模式有什么本质区别？（前者是每层多次高频 all-reduce、对带宽敏感；后者是点对点、对延迟不敏感。）

### 阶段 C：显存优化 —— "让每张卡少装点"

#### 4. ZeRO

- [ ] **P0** ⭐ · [ZeRO: Memory Optimizations Toward Training Trillion Parameter Models](https://arxiv.org/abs/1910.02054) · SC 2020
  - **主旨**：数据并行下每张卡都存一份完整的模型状态（那 16P），极其浪费。ZeRO 把它切成三段逐步分片：**Stage 1 切优化器状态、Stage 2 再切梯度、Stage 3 再切参数**，用通信换显存，且声称通信量几乎不增加。
  - **为什么读 / 读到什么程度**：**精读**。这是理解"为什么今天 7B 模型能在 8 张卡上训练"的关键。必须搞懂：每升一个 stage，省了多少显存、多做了什么通信（all-gather / reduce-scatter）？
  - **前置知识**：第 1、2、3 篇；all-gather 与 reduce-scatter。
  - **建议用时**：4 小时。
  - **中文导读**：可配合 [Microsoft 官方 ZeRO 博客](https://www.microsoft.com/en-us/research/blog/zero-deepspeed-new-system-optimizations-enable-training-models-with-over-100-billion-parameters/) 一起读，博客对 stage 的图示比论文更直观。
  - **读完要能回答**：Stage 3 的参数量是不是真的降到了 1/N？（不是——通信时仍需临时 all-gather 出完整层。）

#### 5. PyTorch FSDP

- [ ] **P0** · [PyTorch FSDP: Experiences on Scaling Fully Sharded Data Parallel](https://arxiv.org/abs/2304.11277) · VLDB 2023
  - **主旨**：把 ZeRO Stage 3 的思想工程化到 PyTorch 原生，讲清了实际落地时的坑：分片时机、参数预取、通信与计算的重叠、混合精度下的 all-gather 精度问题。
  - **为什么读 / 读到什么程度**：**泛读**。重点读第 3 节（设计与实现权衡）和第 5 节（经验教训）。这是"论文到生产"的差距样本。
  - **前置知识**：第 4 篇。
  - **建议用时**：2.5 小时。

#### 6. Reducing Activation Recomputation in Large Transformer Models

- [ ] **P1** · [Reducing Activation Recomputation in Large Transformer Models](https://arxiv.org/abs/2205.05198) · MLSys 2023
  - **主旨**：激活值也是显存大户。这篇提出**序列并行**（把 LayerNorm/Dropout 在序列维度上切开，避免每张卡重复计算）配合**选择性重算**，在几乎不增加通信的前提下把激活显存降下来。
  - **为什么读 / 读到什么程度**：**泛读**。读第 3 节，理解"哪些激活必须重算、哪些可以切分"。
  - **前置知识**：第 3、4 篇；02 模块的重计算。
  - **建议用时**：2 小时。

### 阶段 D：组合与自动化 —— "把它们一起用"

#### 7. Efficient Large-Scale Language Model Training on GPU Clusters (Megatron-DeepSpeed)

- [ ] **P0** ⭐ · [Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-DeepSpeed](https://arxiv.org/abs/2105.13120) · SC 2021
  - **主旨**：当张量并行、流水线并行、数据并行（+ ZeRO-1）同时开启（3D 并行）时，通信量如何随各维度规模变化？这篇给出了量化模型，并解释了为什么**每个维度的并行度不能盲目开大**。
  - **为什么读 / 读到什么程度**：**精读**。这是 04 模块的"总结论文"，把前面几篇统一成一个配置问题。重点读第 3 节的通信量分析与第 4 节的 micro-batch 数选择。
  - **前置知识**：第 1–4、6 篇。
  - **建议用时**：3.5 小时。
  - **读完要能回答**：在给定集群规模下，怎么决定 `TP × PP × DP` 的划分？（约束：TP 不宜超过单机 GPU 数，PP 受气泡比例限制，DP 受全局 batch size 限制。）

#### 8. Alpa

- [ ] **P1** · [Alpa: Automating Inter- and Intra-Operator Parallelism for Distributed Deep Learning](https://arxiv.org/abs/2201.12023) · OSDI 2022
  - **主旨**：把并行策略的选择形式化成编译期搜索问题：算子内并行（intra-op，即张量并行）用 ILP 求解，算子间并行（inter-op，即流水线）用动态规划。目标是让用户写单卡代码，系统自动并行。
  - **为什么读 / 读到什么程度**：**泛读**。读第 3 节的两级优化框架。
  - **前置知识**：第 1、2、3、7 篇。
  - **建议用时**：2 小时。
  - **为什么读它**：它回答"手工调那么多并行参数能不能自动化"，是后面一系列自动并行工作（包括今天的各种 auto-parallel 系统）的起点。

### 阶段 E：MoE 与超大规模

#### 9. GShard 与 Switch Transformers

- [ ] **P1** · [GShard: Scaling Giant Models with Conditional Computation and Automatic Sharding](https://arxiv.org/abs/2006.16668) · ICLR 2021；[Switch Transformers](https://arxiv.org/abs/2101.03961) · JMLR 2022
  - **主旨**：MoE 把参数和计算解耦——参数量可以极大，但每个 token 只激活少部分专家。系统上的核心问题是 **all-to-all 通信** 和 **负载均衡**（用辅助损失让 token 均匀分到各专家）。
  - **为什么读 / 读到什么程度**：**泛读**。两篇合起来读，重点是 GShard 的分片与 all-to-all，以及 Switch 的容量因子（capacity factor）与 token 丢弃机制。
  - **前置知识**：第 3、7 篇（MoE 本质上是 all-to-all 版本的张量并行）。
  - **建议用时**：3 小时。
  - **读完要能回答**：MoE 为什么在推理时更省（激活参数少），在训练时更难（all-to-all、负载不均、容量溢出）？

#### 10. MegaBlocks

- [ ] **P2** · [MegaBlocks: Efficient Sparse Training with Mixture-of-Experts](https://arxiv.org/abs/2211.15841) · MLSys 2023
  - **主旨**：用块稀疏（block-sparse）算子替代传统 MoE 的"按容量填充 + 丢弃 token"做法，不再丢 token，也不再浪费计算。
  - **为什么读 / 读到什么程度**：**泛读**。读摘要 + 方法概览。
  - **建议用时**：1 小时。

#### 11. Ring Attention 与 Zero Bubble Pipeline Parallelism

- [ ] **P1** · [Ring Attention with Blockwise Transformers for Near-Infinite Context](https://arxiv.org/abs/2310.01889) · 2023
  - **主旨**：把长序列按块分到各卡，用环形通信一边算 attention 一边传递 KV，让序列长度不再受单卡显存限制。
  - **为什么读 / 读到什么程度**：**泛读**。理解"通信与计算重叠"这一技巧为什么关键。
  - **建议用时**：1.5 小时。

- [ ] **P1** · [Zero Bubble Pipeline Parallelism](https://arxiv.org/abs/2401.10241) · 2024
  - **主旨**：把反向传播拆成"对输入的梯度"和"对权重的梯度"两部分分别调度，填掉 1F1B 调度中本应空闲的槽位，理论上把气泡降到接近 0。
  - **为什么读 / 读到什么程度**：**泛读**。它是对第 1、2 篇气泡问题的最新回答，是"经典问题仍有优化空间"的范例。
  - **前置知识**：第 1、2 篇。
  - **建议用时**：1.5 小时。

#### 12. 工业界实战报告

- [ ] **P2** · [The Llama 3 Herd of Models](https://arxiv.org/abs/2407.21783) · 2024 —— 重点读其中 **Infra / 训练** 章节，看真实生产训练集群的配置、故障率与并行策略选择。
- [ ] **P2** · [DeepSeek-V3 Technical Report](https://arxiv.org/abs/2412.19437) · 2024 —— 重点读 FP8 训练、MoE 通信与负载均衡、以及无辅助损失的均衡策略。这是当前最有工程参考价值的公开报告之一。
- [ ] **P2** · [MegaScale: Scaling Large Language Model Training to More Than 10,000 GPUs](https://arxiv.org/abs/2402.15627) · NSDI 2025 —— 上万卡规模下的稳定性、通信与容错设计。
- [ ] **P2** · [DeepSpeed 官方博客](https://www.microsoft.com/en-us/research/blog/zero-deepspeed-new-system-optimizations-enable-training-models-with-over-100-billion-parameters/) —— 公式与实现细节的补充读物。
- [ ] **P2** · [DeepSeekMoE](https://arxiv.org/abs/2401.06066) · 2024 —— 更细粒度的专家拆分（共享专家 + 路由专家）。

## 动手验证（这三周必做）

1. **（必做）算清 ZeRO 的三个 stage**：用上面的 16P 表格，手工算出 7B 模型在 8 张卡上，ZeRO Stage 1/2/3 各阶段的每卡显存，以及每步新增的通信量。
2. **（必做）跑一次并行训练**：用 PyTorch FSDP 或 DeepSpeed ZeRO，在单机多卡（或用 `torchrun` 单机多进程模拟）训一个小模型，记录不同 stage/分片策略下的显存峰值与吞吐。**亲手看到显存下降、吞吐变化**，比读十篇论文都管用。
3. **手画调度图**：把 GPipe、1F1B、交错式 1F1B 三种流水线调度各画一遍，标出气泡位置。这是最高频的面试考察点。
4. **推一遍张量并行**：在纸上推导 `Y = GeLU(X·A)` 与 `Z = Y·B` 的列切分/行切分组合，确认通信点在哪儿、有几次。

## 演进链（谁替代了谁）

```
数据并行（每卡一份完整模型）—— 显存不可扩展
    ↓
流水线并行：GPipe（气泡大、显存高）→ PipeDream（1F1B，有陈旧梯度）→ 交错式 → Zero Bubble（2024）
    ↓
张量并行：Megatron-LM（列切+行切配对，每两层一次 all-reduce）→ 序列并行（2023）
    ↓
显存优化：ZeRO-1/2/3（切优化器状态/梯度/参数）→ PyTorch FSDP（原生实现）
    ↓
组合：Megatron-DeepSpeed 的 3D 并行（SC 2021）—— 今天的默认姿势
    ↓
自动化：Alpa（搜索并行策略）
    ↓
规模：MoE（GShard/Switch → MegaBlocks → DeepSeek-V3）与万卡集群（MegaScale）

一句话总结：**所有并行策略的本质，都是在"显存"和"通信"之间换。**
```
